## 1. Overview & Motivation

SaathKhata already handles one-off khata entries and manual bulk charges via product templates. But many vendor–customer relationships in India are subscription-like by nature:

- A milk vendor delivers 2L every morning to 80 households.
- A tiffin service runs Mon–Fri.
- A gym tracks 3 sessions per week for each member.

Today these vendors must manually trigger a "bulk charge" every day (or every delivery day), which is error-prone and adds friction. F005 solves this by letting vendors define **scheduled services** with a recurrence rule, enroll customers, and having the system automatically generate deliveries — and optionally create the corresponding ledger credit entries — at the configured schedule.

This is intentionally separate from any appointment/booking system. A subscription here is an *automatic recurring delivery*, not a customer-initiated booking.

## 2. Current State — What Exists Today

### product_templates table
```
product_templates
  id UUID PK
  vendor_id UUID FK → users
  name VARCHAR
  unit VARCHAR
  price_per_unit DECIMAL
  is_active BOOLEAN
  created_at, updated_at
```

### Bulk Charge Flow (existing)
1. Vendor opens "Templates" section in the app.
2. Selects a template (e.g. "Milk 1L").
3. App hits `POST /templates/bulk-charge` with `{ templateId, items: [{ linkId, quantity }] }`.
4. `TemplateService.bulkCharge()` loops over items:
   - For each `linkId`, creates a `ledger_entries` row with `status='pending'`, `type='credit'`.
   - Calls `linkRepo.adjustBalance(linkId, amount, trx)` immediately (balance adjusted at charge time).
   - Emits `ledger:entry_added` socket event.
   - Enqueues FCM push notification to customer.
5. Returns `{ succeeded: [], failed: [] }`.

### Limitations of the Current Approach
- Vendor must remember to do this every day.
- No calendar view of upcoming or past deliveries.
- No ability to pause delivery for a specific customer.
- No session-tracking mode (e.g. gym: sessions may be prepaid — no per-delivery charge).
- No per-customer quantity customization separate from template.

## 4. Database Schema — Migration 20260037

### 4.1 `scheduled_services`

```sql
CREATE TABLE scheduled_services (
  id                     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vendor_id              UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name                   VARCHAR(150) NOT NULL,
  description            TEXT,
  service_type           VARCHAR(20) NOT NULL CHECK (service_type IN ('product', 'session')),
  unit                   VARCHAR(50),
  default_price_per_unit DECIMAL(10,2),
  schedule_type          VARCHAR(20) NOT NULL CHECK (schedule_type IN ('daily', 'weekly', 'custom_days')),
  delivery_days          INTEGER[],
  -- delivery_days stores day-of-week numbers: 0=Sunday, 1=Monday, ..., 6=Saturday
  -- NULL for 'daily'; [1,2,3,4,5] for Mon-Fri; [1,3,5] for Mon/Wed/Fri
  delivery_time          TIME,
  auto_create_ledger_entry BOOLEAN NOT NULL DEFAULT TRUE,
  is_active              BOOLEAN NOT NULL DEFAULT TRUE,
  created_at             TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
  updated_at             TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_scheduled_services_vendor ON scheduled_services(vendor_id);
CREATE INDEX idx_scheduled_services_active ON scheduled_services(vendor_id, is_active);
```

**Notes:**
- `service_type = 'product'`: physical delivery, creates a ledger credit when delivered.
- `service_type = 'session'`: attendance/session record, `auto_create_ledger_entry` is typically `false` (sessions may be prepaid via membership).
- `delivery_days` must be populated when `schedule_type` is `weekly` or `custom_days`. Ignored when `schedule_type = 'daily'`.
- `delivery_time` is informational — the cron runs at midnight and generates the day's deliveries; this field is shown in the UI as a hint to the vendor/staff.

### 4.2 `service_subscriptions`

```sql
CREATE TABLE service_subscriptions (
  id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  service_id            UUID NOT NULL REFERENCES scheduled_services(id) ON DELETE CASCADE,
  link_id               UUID NOT NULL REFERENCES vendor_customer_links(id) ON DELETE CASCADE,
  vendor_id             UUID NOT NULL REFERENCES users(id),
  customer_id           UUID NOT NULL REFERENCES users(id),
  quantity_per_delivery DECIMAL(10,3) NOT NULL DEFAULT 1,
  custom_price_per_unit DECIMAL(10,2),
  -- NULL = use service's default_price_per_unit
  start_date            DATE NOT NULL,
  end_date              DATE,
  -- NULL = subscription is indefinite
  is_active             BOOLEAN NOT NULL DEFAULT TRUE,
  is_paused             BOOLEAN NOT NULL DEFAULT FALSE,
  paused_until          DATE,
  -- NULL = paused indefinitely (until manually resumed)
  created_at            TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
  updated_at            TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),

  CONSTRAINT uq_service_customer UNIQUE (service_id, customer_id)
);

CREATE INDEX idx_subscriptions_service ON service_subscriptions(service_id);
CREATE INDEX idx_subscriptions_link ON service_subscriptions(link_id);
CREATE INDEX idx_subscriptions_vendor ON service_subscriptions(vendor_id);
CREATE INDEX idx_subscriptions_customer ON service_subscriptions(customer_id);
CREATE INDEX idx_subscriptions_active ON service_subscriptions(vendor_id, is_active, is_paused);
```

**Notes:**
- `UNIQUE(service_id, customer_id)` prevents double-enrollment. A customer can subscribe to multiple services from the same vendor, but only once per service.
- `quantity_per_delivery`: e.g. 2.0 for "2 liters of milk daily".
- `custom_price_per_unit`: override allows vendor to give specific customers a different rate (e.g. a long-time customer gets a discount).
- `paused_until`: if set, the cron skips generating deliveries while `today < paused_until`. On or after `paused_until`, the subscription is auto-resumed (cron sets `is_paused = false, paused_until = null`).

### 4.3 `scheduled_deliveries`

```sql
CREATE TABLE scheduled_deliveries (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subscription_id  UUID NOT NULL REFERENCES service_subscriptions(id) ON DELETE CASCADE,
  service_id       UUID NOT NULL REFERENCES scheduled_services(id),
  link_id          UUID NOT NULL REFERENCES vendor_customer_links(id),
  vendor_id        UUID NOT NULL REFERENCES users(id),
  customer_id      UUID NOT NULL REFERENCES users(id),
  scheduled_date   DATE NOT NULL,
  status           VARCHAR(20) NOT NULL DEFAULT 'scheduled'
                     CHECK (status IN ('scheduled', 'delivered', 'skipped', 'failed')),
  ledger_entry_id  UUID REFERENCES ledger_entries(id),
  -- Populated if auto_create_ledger_entry=true and entry was created successfully
  delivered_at     TIMESTAMP WITH TIME ZONE,
  notes            TEXT,
  created_at       TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),

  CONSTRAINT uq_delivery_subscription_date UNIQUE (subscription_id, scheduled_date)
  -- Prevents duplicate delivery records for the same subscription on the same day
);

CREATE INDEX idx_deliveries_vendor_date ON scheduled_deliveries(vendor_id, scheduled_date);
CREATE INDEX idx_deliveries_link ON scheduled_deliveries(link_id);
CREATE INDEX idx_deliveries_service ON scheduled_deliveries(service_id);
CREATE INDEX idx_deliveries_status ON scheduled_deliveries(vendor_id, status, scheduled_date);
CREATE INDEX idx_deliveries_ledger_entry ON scheduled_deliveries(ledger_entry_id);
```

**Status Transitions:**
```
scheduled → delivered   (cron auto-delivers, or manual mark-delivered)
scheduled → skipped     (vendor/staff skips for a specific delivery)
scheduled → failed      (cron attempted ledger entry creation and it failed)
delivered → skipped     (possible correction: un-deliver)
```

## 7. Cron Job — BullMQ Scheduled Delivery Worker

### Queue Setup

Add to `src/infrastructure/jobs/queues/index.ts`:
```typescript
export const scheduleDeliveriesQueue = new Queue('scheduled-deliveries', {
  connection: redisClient,
  defaultJobOptions: { attempts: 3, backoff: { type: 'exponential', delay: 60_000 } },
});

// Repeatable job: run at midnight IST (UTC+5:30 = 18:30 UTC previous day)
await scheduleDeliveriesQueue.add(
  'generate-daily-deliveries',
  {},
  { repeat: { cron: '30 18 * * *' } },  // 00:00 IST
);
```

### Worker: `schedule-delivery.processor.ts`

```typescript
// Pseudocode — implement fully in TypeScript

async function processDailyDeliveries(job: Job) {
  const today = new Date();
  today.setHours(0, 0, 0, 0);
  const todayDow = today.getDay(); // 0=Sun … 6=Sat

  // 1. Auto-resume subscriptions where paused_until <= today
  await db('service_subscriptions')
    .where('is_paused', true)
    .where('paused_until', '<=', today)
    .whereNotNull('paused_until')
    .update({ is_paused: false, paused_until: null, updated_at: new Date() });

  // 2. Fetch all active subscriptions for services that deliver today
  const subscriptions = await db('service_subscriptions as ss')
    .join('scheduled_services as svc', 'ss.service_id', 'svc.id')
    .join('vendor_customer_links as vcl', 'ss.link_id', 'vcl.id')
    .where('ss.is_active', true)
    .where('ss.is_paused', false)
    .where('svc.is_active', true)
    .where('vcl.is_active', true)
    .where(function() {
      this.where('ss.start_date', '<=', today);
    })
    .where(function() {
      this.whereNull('ss.end_date').orWhere('ss.end_date', '>=', today);
    })
    .where(function() {
      // daily → always; weekly/custom_days → only if today's DOW is in delivery_days
      this.where('svc.schedule_type', 'daily')
          .orWhere(function() {
            this.whereIn('svc.schedule_type', ['weekly', 'custom_days'])
                .whereRaw('? = ANY(svc.delivery_days)', [todayDow]);
          });
    })
    .select('ss.*', 'svc.auto_create_ledger_entry', 'svc.default_price_per_unit',
            'svc.unit', 'svc.name as service_name');

  // 3. For each subscription, create a scheduled_delivery record + optional ledger entry
  for (const sub of subscriptions) {
    const trx = await db.transaction();
    try {
      // Skip if delivery record already exists (idempotency guard)
      const existing = await db('scheduled_deliveries')
        .where({ subscription_id: sub.id, scheduled_date: today })
        .first();
      if (existing) { await trx.rollback(); continue; }

      // Compute charge amount
      const pricePerUnit = sub.custom_price_per_unit ?? sub.default_price_per_unit;
      const amount = pricePerUnit
        ? parseFloat((sub.quantity_per_delivery * pricePerUnit).toFixed(2))
        : 0;

      let ledgerEntryId: string | null = null;

      if (sub.auto_create_ledger_entry && amount > 0) {
        const [entry] = await db('ledger_entries')
          .transacting(trx)
          .insert({
            link_id: sub.link_id,
            vendor_id: sub.vendor_id,
            customer_id: sub.customer_id,
            amount: amount.toFixed(2),
            type: 'credit',
            date: today,
            description: sub.service_name,
            quantity: sub.quantity_per_delivery,
            unit: sub.unit,
            // F007: vendor-side → auto_confirmed immediately
            status: 'auto_confirmed',
            confirmed_at: new Date(),
            is_locked: true,
            dispute_reason: null,
            attachment_url: null,
            created_by: sub.vendor_id, // system creates on vendor's behalf
          })
          .returning('*');

        // Adjust balance immediately (auto_confirmed path)
        await linkRepo.adjustBalance(sub.link_id, amount, trx);
        ledgerEntryId = entry.id;
      }

      // Create the delivery record
      const [delivery] = await db('scheduled_deliveries')
        .transacting(trx)
        .insert({
          subscription_id: sub.id,
          service_id: sub.service_id,
          link_id: sub.link_id,
          vendor_id: sub.vendor_id,
          customer_id: sub.customer_id,
          scheduled_date: today,
          status: sub.auto_create_ledger_entry && amount > 0 ? 'delivered' : 'scheduled',
          ledger_entry_id: ledgerEntryId,
          delivered_at: sub.auto_create_ledger_entry && amount > 0 ? new Date() : null,
        })
        .returning('*');

      await trx.commit();

      // Emit socket event
      emitLedgerEvent('ledger:entry_added', sub.link_id, { linkId: sub.link_id, delivery });

      // Push notification to customer
      await enqueueNotification({
        recipientUserId: sub.customer_id,
        type: 'delivery_auto_created',
        title: sub.service_name,
        body: amount > 0
          ? `₹${amount} — ${sub.quantity_per_delivery} ${sub.unit} delivered today`
          : `${sub.service_name} session recorded for today`,
        data: { deliveryId: delivery.id, linkId: sub.link_id, amount },
      });

    } catch (err) {
      await trx.rollback();
      logger.error('schedule-delivery: failed for subscription', { subscriptionId: sub.id, err });
      // Mark delivery as failed (best-effort, outside trx)
      await db('scheduled_deliveries').insert({
        subscription_id: sub.id,
        service_id: sub.service_id,
        link_id: sub.link_id,
        vendor_id: sub.vendor_id,
        customer_id: sub.customer_id,
        scheduled_date: today,
        status: 'failed',
        notes: err instanceof Error ? err.message : 'Unknown error',
      }).onConflict(['subscription_id', 'scheduled_date']).ignore();
    }
  }
}
```

### Idempotency
The `UNIQUE(subscription_id, scheduled_date)` constraint on `scheduled_deliveries` acts as the primary idempotency guard. The worker also checks for existing records before processing. If BullMQ retries the job (e.g., after a crash), the second run will skip subscriptions that already have a delivery record for today.

## 8. Ledger Integration — Auto-Created Entries

When `auto_create_ledger_entry = true` AND the subscription has a non-zero price:
- The cron worker creates a `ledger_entries` row with `status = 'auto_confirmed'`, `is_locked = true`.
- This follows the same auto_confirmed path as F007 (vendor-side credits are authoritative).
- `adjustBalance()` is called in the same transaction — the customer's balance increases immediately.
- `ledger_entry_id` on the `scheduled_deliveries` row references this entry.

When `auto_create_ledger_entry = false` (session tracking, or free services):
- Only a `scheduled_deliveries` row is created.
- No ledger entry, no balance change.
- Staff/vendor can still manually call `PATCH /schedule/deliveries/:id/mark-delivered` to create a ledger entry after the fact if needed.

### Manual Mark-Delivered Flow (`PATCH /schedule/deliveries/:id/mark-delivered`)
Used when the cron status is `'scheduled'` and the delivery happened but auto-ledger was off, or to confirm a session was attended:
1. Fetch delivery record; verify caller is vendor or staff for that vendor.
2. If `ledger_entry_id` is already set → 409 (already processed).
3. If `auto_create_ledger_entry = true` and `amount > 0`: create ledger entry + adjust balance in transaction.
4. Update delivery: `status = 'delivered', delivered_at = now(), ledger_entry_id = <new entry id>`.
5. Emit socket event + push notification.

## 9. Socket & Real-Time Events

Existing socket rooms `user:{userId}` and `link:{linkId}` are reused.

| Event | Room | Payload | When |
|-------|------|---------|------|
| `ledger:entry_added` | `link:{linkId}` | `{ linkId, entry: LedgerEntryResponse }` | Cron auto-creates ledger entry |
| `schedule:delivery_created` | `user:{vendorId}` | `{ delivery: ScheduledDeliveryResponse }` | Cron creates delivery record |
| `schedule:delivery_updated` | `link:{linkId}` | `{ delivery: ScheduledDeliveryResponse }` | Mark-delivered or skip |

The `schedule:delivery_created` and `schedule:delivery_updated` events require emitting from `ledger-socket.ts` or a new `schedule-socket.ts` helper. Prefer adding an `emitScheduleEvent()` function in a new `src/infrastructure/socket/schedule-socket.ts`.

## 16. How Auto-Delivery Connects to the Ledger

```
Cron fires at 00:00 IST
          │
          ▼
For each active subscription that delivers today:
          │
          ├─► Create scheduled_deliveries record (status: 'delivered')
          │
          └─► If auto_create_ledger_entry=true AND price > 0:
                  │
                  ▼
              INSERT ledger_entries:
                type='credit', status='auto_confirmed',
                is_locked=true, confirmed_at=NOW()
                  │
                  ▼
              adjustBalance(linkId, +amount, trx)
                  │
                  ▼
              Set scheduled_deliveries.ledger_entry_id = entry.id
                  │
                  ▼
              Emit ledger:entry_added socket event
                  │
                  ▼
              Enqueue FCM push to customer
```

The resulting ledger entry is identical in structure to a manually created vendor credit — except:
- `created_by = vendor_id` (system creates on vendor's behalf)
- `description = service.name`
- `status = 'auto_confirmed'` (follows F007 rules — vendor credit is authoritative)

From the customer's `SharedLedgerScreen`, this entry appears in the ledger exactly like any other confirmed credit. It shows the service name as description and is locked (not disputable).

## 18. Subscription Pause / Resume Logic

### Pause
`PATCH /schedule/subscriptions/:id/pause` body: `{ pausedUntil?: string /* ISO date */ }`

- If `pausedUntil` is provided: subscription is paused until (not including) that date.
- If `pausedUntil` is null/omitted: subscription is paused indefinitely.
- Sets: `is_paused = true, paused_until = pausedUntil`.
- Cron worker skips this subscription until `today >= paused_until`.
- When `paused_until` is reached, cron auto-resumes: `is_paused = false, paused_until = null`.

### Resume
`PATCH /schedule/subscriptions/:id/resume`
- Sets `is_paused = false, paused_until = null` immediately.
- Does NOT backfill missed deliveries during the pause period (see §21).

### Pause UX
- In `ServiceDetailScreen` (vendor): each customer row has a "Pause" button → opens a date picker asking "Pause until when? (leave blank for indefinite)".
- Paused customers show a "Paused" badge with the resume date.

## 19. Service Price Change Handling

When a vendor changes `default_price_per_unit` on a service:
- Existing subscriptions with `custom_price_per_unit = null` will automatically use the new price from the next cron run.
- Existing subscriptions with `custom_price_per_unit != null` are unaffected (their override takes precedence).
- Past `scheduled_deliveries` records and their associated `ledger_entries` are immutable (already confirmed and locked).
- **No retroactive recalculation is done.**
- The vendor should be warned in the `EditServiceSheet`: "Changing the price will affect all future deliveries for customers without a custom price."

## 20. Customer Removed from Link

If a vendor deactivates a `vendor_customer_links` row (or the link becomes inactive):
- The `service_subscriptions` row for that customer is automatically inactive because the `ON DELETE CASCADE` on `link_id` removes the subscription. (Or: add a trigger/constraint to set `is_active = false` when the link is deactivated.)
- Safest approach: the cron worker's query already JOINs `vendor_customer_links` and filters `vcl.is_active = true`, so inactive-link subscriptions are silently skipped.
- The vendor should also explicitly deactivate the subscription via `DELETE /schedule/subscriptions/:id` when removing a customer.

## 21. Delivery Window Missed (Backfill Policy)

**Policy: No automatic backfill.**

If the cron job fails to run on a given day (server outage, Redis crash, etc.), no deliveries are generated for that day. The vendor can:
1. Manually mark individual deliveries as delivered via `PATCH /schedule/deliveries/:id/mark-delivered` — but this requires the `scheduled_deliveries` record to already exist.
2. If the record doesn't exist (cron never ran), the vendor can use the existing manual bulk-charge flow (`POST /templates/bulk-charge`) as a fallback.

**Backfill helper (optional, future):** A one-off admin endpoint `POST /admin/schedule/backfill?date=` that runs the cron logic for a specific past date. Not part of F005 scope but should be documented here as a future consideration.

**Detection:** The cron job should record a "heartbeat" in a `job_runs` table or Redis key on each successful execution. A monitoring alert fires if no heartbeat is received within 25 hours.

## 22. Edge Cases

| Scenario | Handling |
|----------|----------|
| Subscription `start_date` is today, but cron ran before the subscription was created | `scheduled_date >= start_date` check in cron; this sub will be picked up on the next day's run. Vendor can manually trigger for today. |
| Subscription `end_date` is today | Cron check `end_date >= today` includes today, so the last delivery IS created. |
| Service is deactivated mid-day | Active subscriptions for this service will be skipped on next cron run. In-progress transactions are safe (checked at query time). |
| Cron creates a duplicate (Redis crash after commit, job retried) | `UNIQUE(subscription_id, scheduled_date)` prevents duplicate rows. `ON CONFLICT DO NOTHING`. |
| `price_per_unit = 0` or NULL and `auto_create_ledger_entry = true` | Worker skips ledger entry creation (amount = 0). Delivery record is still created with `status = 'delivered'`. Add warning in UI. |
| Customer has zero balance but cron keeps adding credits | This is normal — balance goes negative (customer owes more). SaathKhata does not enforce credit limits. |
| Two subscriptions for the same customer in the same service (race condition on enroll) | `UNIQUE(service_id, customer_id)` on `service_subscriptions` prevents this at DB level. |
| Staff marks delivered for a delivery that was already auto-delivered by cron | `ledger_entry_id IS NOT NULL` check → 409 Conflict response. |
| Timezone: India is IST (UTC+5:30), cron runs at 18:30 UTC | BullMQ cron uses UTC. `'30 18 * * *'` = 00:00 IST. Scheduled date stored as IST `DATE` in DB using `AT TIME ZONE 'Asia/Kolkata'`. |

## 23. Bulk "Deliver All Today" Button

Available in `ScheduleCalendarScreen` (vendor) and `ServiceDetailScreen` (vendor) for today's deliveries.

**Flow:**
1. Vendor taps "Deliver All Today".
2. App shows confirmation: "Deliver [N] scheduled items today? This will add ₹[total] to [N] customers' khatas."
3. On confirm: calls `POST /schedule/deliveries/bulk-mark-delivered` with `{ date, serviceId? }`.
4. Backend endpoint runs the same logic as `mark-delivered` for all `status='scheduled'` deliveries for that date/service.
5. Returns `{ succeeded: N, failed: [] }`.
6. UI shows success snackbar: "Delivered for N customers."

This is distinct from the existing `POST /templates/bulk-charge` — that creates new ledger entries; this marks *existing scheduled delivery records* as delivered.

## 25. Rollback Considerations

### Feature Flag
Add `ENABLE_SCHEDULE_MODULE=true` to `.env`. The `schedule.routes.ts` is only mounted if this env var is set. This allows deploying the migration without activating the feature.

### Database Rollback (`migration 20260037 down`)
```sql
DROP TABLE IF EXISTS scheduled_deliveries;
DROP TABLE IF EXISTS service_subscriptions;
DROP TABLE IF EXISTS scheduled_services;
```
Ledger entries created by the cron are standard `ledger_entries` rows and do not need to be deleted on rollback (they reflect real deliveries).

### BullMQ Rollback
- Remove the repeatable job: `await scheduleDeliveriesQueue.removeRepeatable('generate-daily-deliveries', { cron: '30 18 * * *' })`.
- Or simply disable the worker process and drain the queue.

## 26. Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Cron misses a day (Redis unavailable) | Low | High (missed deliveries not auto-created) | BullMQ persistence in Redis with AOF; monitor heartbeat; manual backfill endpoint. |
| Timezone bug (cron runs on wrong day for IST) | Medium | Medium (deliveries created a day early/late) | Use `'30 18 * * *'` UTC explicitly; add integration test asserting scheduled_date = IST date. |
| N+1 in cron (one transaction per subscription) | Low | Medium (slow for 10,000 subscriptions) | Batch DB writes; use `Promise.all` in chunks of 100. |
| Price changed mid-cycle, customer expects old price | Medium | Low (business dispute) | Show "last charged price" in subscription history; document that price changes take effect next delivery. |
| `service_subscriptions` grows unbounded (inactive rows) | Low | Low | Periodic cleanup job or soft-delete with archival. |
| Duplicate ledger entries if cron + manual deliver race | Low | High (double charge) | `ledger_entry_id IS NOT NULL` guard in `mark-delivered` endpoint; DB unique constraint. |
